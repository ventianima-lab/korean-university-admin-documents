# Procurement forms and evidence pages

Read this reference before proposing a programme budget, including a chat estimate, or drafting or revising purchase preapproval, purchase inspection records, expense settlement, vendor quotations, receipt attachment forms, or evidence-photo pages. Use the user's current edited files as the baseline. Keep active records in their working folder when the user requests that; organization is not permission to archive them.

## Permission and factual fields

- A request to prepare a document includes the user's clearance with the named vendor or party for that preparation and requested use of supplied names, seals, and signatures. Do not ask whether that permission exists or request it again.
- Treat dates, amounts, and party instructions supplied by the user as source facts. Distinguish missing business data from permission; inspect context and files before asking only for a value necessary to finish. Do not infer missing approval states or create an absent signature image.
- Use an existing supplied stamp or signature image when requested. Preserve its identity and proportions; do not draw, generate, or substitute a new seal. Preparation does not authorize sending or submission.

## Preapproval packet completeness

For a continuing same-programme preapproval, before drafting, inspect the actual preapproval-stage files, form headings and grouping in the nearest comparable prior periods, including two preceding periods when available. Independently inventory each companion role, its source file and period, its stage and whether it recurs; also inspect each letter’s actual attachment line, the current request and applicable current instructions. A previous letter’s attachment list is not an exhaustive inventory of separately maintained forms.

Compare the recurring roles with the current user-selected scope, selected-form allowlist or exclusions, user-managed items, and the current letter’s planned attachments. Where a repeated companion clearly belongs to the requested continuation and is neither excluded nor user-managed, prepare it from an eligible same-programme master in its established grouping within the authorized scope. Do not add every historical form, change an attachment line solely because a prior folder contains a file, or assert that a precedent is an office-mandated requirement. An explicit user-selected list, exclusion, or narrower request controls. If a relevant role’s scope, source master, or current applicability cannot be resolved, record it as pending and identify the specific uncertainty.

Before reporting preparation complete, reconcile the independent role inventory against the inspected saved output for each in-scope role, explicit exclusions, user-managed items, and any pending items. Verify each output’s role, current period and intended grouping, and separately reconcile the letter’s actual attachment list with its applicable files; a correct cover letter or matching filenames alone cannot establish companion coverage. An unresolved in-scope role blocks a complete-preparation claim. A user-excluded or out-of-scope role does not. Keep preparation status separate from institutional submission requirements, acceptance, and approval.

When asked whether the materials are sufficient for advance approval, inspect the current saved letter and its attachment line, current programme-specific requirements, and the prior same-programme letter's actual attachment list. Inventory advance planned rosters and other preparable attachments separately from post-event signed attendance, minutes, photos, and receipts. For each item, distinguish a current requirement, a conditional requirement, the user's requested preparation, and a prior-year precedent. A precedent does not prove a current requirement, and a generic list of post-event evidence does not answer an advance-submission question. Cite the exact source and location, identify unresolved programme-specific requirements for the responsible office, and do not guarantee acceptance without an actual approval.

When the user requests an activity-specific plan within an existing reference attachment, the generic reference alone does not satisfy that request. Map each requested detail, such as timing, activity stages, item-specific methods, recording or follow-up discussion, to its saved location. Preserve the source-backed information and describe unconfirmed choices as plans; when the user authorizes integrating or rebuilding the reference table, do not freeze its old graphic or placement. Do not invent actual results or prescribed methods. Verify the requested details in the saved document and inspect the complete page renders; do not add a plan when only the reference is requested.

When a plan must fit a user-specified page size and count, independently inventory the requested activities, confirmed responsibilities and required table information, including relevant categories, populations, units and alternatives. If a source table is an image, inspect and transcribe its required contents; a media hash or text extraction alone does not verify a rebuilt table. Where the user explicitly identifies who supplies equipment, retain and check that responsibility rather than replacing it with a vague availability check. If the user requests a compact integrated layout and permits table redesign, combine the plan and table accordingly, using the specified institutional style or supplied master and readable print sizing. Compare the saved editable fields against the independent inventory with `scripts/validate_hwpx_opensource.py <saved.hwpx> --fields <inventory.json> --fields-only`, and check any image-only content visually. Reopen the exact saved HWPX, check its actual physical page count and requested paper size, and inspect the full current render for completeness, clipping, legibility and balanced use of space. A field-only or preservation test does not prove page count, visual balance or transcribed image content. If all required information cannot fit legibly, report the unresolved conflict instead of claiming completion or silently dropping content.

Do not introduce a source or reference note in the document merely to justify the work; include one only when requested, required, or part of protected template wording. Keep supporting sources in the independent verification or response, and check saved body and preview for an unwanted note.

For each planned-attendee roster, independently record its output role and submission stage; programme and year; the exact layout source and its own role, stage and programme; and any separate authority source and passage establishing the current requirement or prescribed form. Record institutional requirement status as required, conditional, optional or unverified only when supported, and record the user's request separately. Inspect the current notice and manual, any applicable office-issued attachments and same-programme precedent. A same-year departmental example from another activity is a reference or adapted precedent, not proof that its layout is prescribed or accepted for the target programme; a current signed-attendance form does not establish that a planned roster is mandatory or prescribe its layout. Absence from a searched manual alone does not prove that no designated form exists.

Before handoff, compare each actual roster and the user-facing explanation or submission claim against this source/role/stage inventory. Name an adapted source as an adaptation, not an official designated form, unless the applicable authority establishes that designation. Do not say an advance roster is required, optional or submission-ready without the corresponding evidence; identify the precise unanswered question for the responsible office. A user-requested roster and a required roster are different facts. Where the designated form cannot be established, follow the template-first fallback and any explicit authorization for a provisional example; keep provenance and unresolved status outside the official form. A layout, openability, or title match alone does not pass this check.

When the user says a planned-attendee list must have no signature field, keep the advance roster and the post-event sign-in sheet as distinct roles. Do not present a sign-in sheet as an official designated advance-roster template. If the user explicitly selects that specific sign-in form for adaptation, use that source and remove the signature wording and signing fields as directed; identify it as an adaptation, not an institution-prescribed advance form. Otherwise use an applicable official planned-roster source, or another source only if authorized; if the user requires an official form and none can be found, leave it pending rather than inventing a layout. Check the roster and the letter's attachment label together.

For multiple roster tables in one saved file, give a separate entry for each. When adapting a sign-in source, the helper inventories every table in every saved section; list separately inspected non-roster layout tables as `non_roster_tables` entries `{section, table, evidence}` on one roster entry so an unaccounted table blocks the check. The helper checks every section's signature text, the exact listed headers, each listed grid row, and the adapted document's table inventory; a blank added grid column fails. It cannot prove a table's stated role or detect an unlabeled line or graphical signing field. Independently inspect every table, all rows and the current complete render before delivery.

The same `--planned-roster-check` also requires a `source_header` with source `section`, `table`, `row` and `columns` entries `{col, source_col, text}` mapping every output column to the actual selected template header. Supply `expected_cells` for every grid row and column, including empty cells as `parts: []`. For each nonempty cell, list ordered `parts` that reproduce its exact saved text: a value part has `kind: "value"`, the source-header `field`, exact `text`, and independent `source`; a punctuation-only literal part has `kind: "literal"`, exact `text`, and its own source. A source is an actual HWPX `source_cell` with `path`, `section`, `table`, `row` and `col`; a `verified_reference` with `reference`, `location` and a `quote` containing the value; or a verified `user_edited_snapshot`. Do not derive the expected value from the generated candidate. The checker compares the actual source headers and every cell, flags source-header mismatches and fields not present in that header, and detects a grade expression hidden inside a different field. A literal-only placeholder requires explicit user authorization; unsupported blanks remain empty.

An explicitly requested additional field uses `authorization: {kind: "explicit_user_instruction", reference, quote}` on that value part; the quoted instruction must identify the field. If the user explicitly changed the header, record `header_authorization` with the same fields plus `field`. To preserve content or a header already edited by the user, record `user_snapshot` or `user_header_snapshot` with `kind: "user_edited_snapshot"`, a distinct pre-edit snapshot `path`, its `sha256`, `reference`, and its `section`, `table`, `row`, `col`; the exact saved cell must match that snapshot. Use it only for a genuinely user-edited baseline, not a prior agent-generated value. A verified reference or quoted instruction remains a human-reviewed assertion: the helper does not authenticate it, discover omitted labels, or inspect image-only content. Do not reword evidence merely to pass; resolve unverified mappings before handoff.

For an HWPX covering letter with an attachment list, run `scripts/verify_required_packet.py <private-inventory.json> --attachment-check` after independently enumerating the exact packet. In `attachment_check`, record the saved `letter`, exact `start_marker` and `end_marker`, and contiguous top-level `paragraphs` (`section`, zero-based `paragraph`, ordered `segments` with exact `text` and `kind`: `context` or `item`). Each item maps `entries` to independently inspected roles. One combined file can contain multiple inspected document units. For grouped entries it requires an explicit `각 ...부` count. With both options enabled, each standalone planned-roster path must also be mapped as a planned-roster attachment. A declared location does not prove that the file contains the stated content or that the selected file list is exhaustive; inspect both independently.

When correcting a user-edited letter, snapshot the current live file first. Compare the candidate with that snapshot using `scripts/verify_hwpx_followup.py`, excluding only the attachment paragraphs that must change, and check the exact complete text of those paragraphs using `--fields-only` with expectations independently derived from the latest user file and authorized edits. Recheck the live hash immediately before replacement. Then run the attachment gate above; these checks complement, rather than replace, inspection of protected content inside edited blocks and the rendered page.

Before declaring an advance packet complete, inspect the full source checklist for each relevant expense category, operating method and stage. Transcribe every source row before deciding whether it applies; split combined rows into distinct document or signatory roles so a listed roster or a separate safety-related role cannot disappear inside another item. Record the actual event setting, the condition for each row, and the source of the applicability decision. Keep a user-confirmed operating instruction distinct from a written institutional rule; a broad programme checklist alone does not prove that every safety document applies to every indoor or off-campus activity. Mark each row required, conditional/pending or not applicable with its specific supported reason, and do not create an excluded form. If the source or condition remains unresolved, do not claim full approval readiness; identify the specific office confirmation. Review post-event evidence separately without treating it as an advance attachment.

When outside personnel participate and their role or personal-document applicability matters, run `scripts/verify_required_packet.py <private-inventory.json> --role-expense-check` before claiming packet completeness. Independently inspect the actual activity, each relevant personnel-role condition and each actual or planned expense category; a fee checklist and a role-triggered requirement are separate. Do not infer an instructor role or personal-document obligation from outside attendance or a headcount. A zero fee can make a payment-triggered row inapplicable, but cannot resolve a separate special-lecture or other role condition. Treat an unconfirmed role or condition as pending and identify the question for the responsible office. Compare every role label in the current saved letter with independently sourced participant roles; a conflict stays pending, not silently corrected or accepted.

The private `role_expense_review` contains `stage` (`planned` or `actual`), `payments`, and `groups`. Partition groups by independently established role and fee allocation. Each payment has `kind` (`instructor_fee`, `consulting_fee`, or `other`), `category`, nonnegative integer `amount`, and an `evidence` object with `kind`, `reference`, `location`, and exact `quote`. For each group explicitly record both fee kinds, including source-supported zero amounts; positive categories must also appear in `expense_reviews`. Evidence kinds for payments are `user_instruction`, `office_confirmation`, `prior_record`, `approved_plan`, or `settlement_record`. Do not call planned sums actual payments.

Each group has a unique `id`, an `actual_role` with `kind` (`support`, `instructor`, `assistant_instructor`, `consultant`, or `participant`) and independent `evidence` (`user_instruction`, `office_confirmation`, or `prior_record` plus reference, location and quote), and `letter_labels` covering its saved HWPX letter labels. For each label record `path`, `section`, and either a zero-based top-level `paragraph` or zero-based `table`, `row`, and `cell` ordinals; `label` is the exact complete saved paragraph or cell text, excluding surrounding whitespace. The checker reads that saved text, compares its recognized role with the independent role, and blocks on a mismatch, missing location, unknown label, or using the letter itself as its only prior-record role evidence. Examine all relevant labels and image-only text separately; a generic participant label does not establish an instructor role.

Each group also has `documents` entries for reviewing `resume` and `background_check`, plus `privacy_consent` when relevant; recording a review does not require creating a document. For each, record `status` (`required`, `not_applicable`, or `pending`), both `fee_conditions` (`kind`, `effect`: `required_if_paid` or source-supported `no_requirement`, and governing `policy`), and every relevant independent `role_conditions` entry (`kind`: `special_lecture`, `instructor`, `assistant_instructor`, or `consultant`; `matched`: `yes`, `no`, or `unknown`; governing `policy`; and independent role `evidence` when known). Every policy has a source `reference`, exact `location` and `quote`. A required document maps to a `requirement_id`; a separately user-requested but non-required document may retain that mapping only with a `user_request` evidence object. The helper requires source and condition coverage, blocks unknown role conditions, unsupported claims, missing fee reviews and contradictory exclusions, and checks that role evidence addresses the role rather than only a fee or headcount. If a role quote or saved label cannot be recognized, keep the outcome pending; do not rewrite source evidence to make the check pass. The helper cannot authenticate evidence, identify omitted source conditions or participants, determine the meaning of a rule, inspect images, or replace an office decision. Review those independently and report the uncertainty.

Where the relevant current checklist is a cell in an HWPX manual, run `scripts/verify_required_packet.py <private-inventory.json> --advance-source-check`. In each relevant `expense_reviews` entry, include `source_cells` with the HWPX `path`, `section`, zero-based `table`, `row` and `cell` ordinal, `stage` (`advance` or `post`), `activity_context`, `applicability_basis`, and ordered `segments`. Each segment has exact source `text`, `kind` (`context` or `item`), and, for advance item segments, an `item` equal to its `items` label. Split a source row into several item segments when it contains separate obligations; include headings and connectors as context. The helper compares the ordered non-whitespace characters of the segments with the complete cell text, detects unmapped advance segments and explicit Korean stage-label mismatches, and retains the existing required/pending/not-applicable checks. Cells combining both stage headings need an equivalent independent stage review instead. Test selected source cells and locations against the actual checklist, including any separate post-event cell. This check cannot establish that all relevant source cells were selected, classify obligations hidden inside a context segment, verify the stated applicability, or grant approval; independently compare the complete source and the event-specific evidence before handoff. For non-HWPX or non-table sources, perform an equivalent independent source-to-row review without pretending this helper verified them.

## Before answering and preparing post-event forms

Before asking whether a phased result report is intermediate or final, inspect the current claim number, budget balance, programme plan and evidence of continuing activity. When those sources together establish that the programme is continuing and the current claim is an initial installment against funds reserved for further activity, select the intermediate status without asking the user to repeat what the records already establish. A first claim or unspent balance alone does not prove continuation; if closure or future activity remains genuinely uncertain after checking the sources, ask one focused question. An explicit user designation controls. After saving, verify the selected status checkbox and preserve the current claim number, user-entered budget, balance, dates and payment fields.

Before quoting an amount or asking the user to confirm it, inspect the live preapproval and payment forms and bind the instructor category, rates, duration, manuscript fee, and approval status to their governing sources. Prior conversations or memory are search clues, not the basis for superseding a user-confirmed approved category. If they conflict, explain the current source and recalculate before asking. On a correction, discard the earlier expected-value map and verify the corrected category, each amount, and total in every in-scope saved form.

For post-event reports, proactively read supplied signed attendance and survey scans before leaving outcome fields blank. Reconcile actual signatures and each answered question against the roster, document the response denominator, and use the latest complete scan. Distinguish a payment application from a completed transfer using required existing fields and the approved workflow. Do not add a parenthetical status note or restore one the user removed merely to explain the distinction; if the form lacks an approved status field, communicate the status outside the form unless the governing authority requires it there. Preserve unsupported signer-controlled fields.

When the user asks which form should contain a specific item, answer the form and the relevant attachment slot, rather than only saying the evidence can be included. Check the current programme notice, the actual expense category and its itemized requirements, and whether each requirement is mandatory or applies only conditionally. A programme list of event photos does not resolve whether a purchase photo belongs in an inspection report. Current rules and the form's labels govern; prior cases are context only. If the programme says to submit ID and bank copies separately without designating a form, do not claim a numbered form from a different programme is required; identify any borrowed unnumbered attachment sheet as a presentation aid.

## Expense-resolution precedent fidelity

When the user asks to follow an earlier expense resolution, read the exact saved narrative field before drafting; a flattened accessibility summary cannot establish spaces or line breaks. Freeze its labels, section order, empty lines, indentation, punctuation, separator line, and attachment notation as a literal template. Replace only source-backed transaction facts. Do not independently expand the outline or normalize its separator or spacing in the name of prose quality. Map the attachment list to the actual uploaded files and grouping; a combined scan is one file, and an uploaded attachment does not excuse an omitted narrative list. After saving, reopen the record and compare the complete raw field character for character against an independently prepared expected body, including all protected whitespace. Reconcile the title, amount, department, project, account code, payee, payment account, invoice date, supply amount, tax, and attachment roles against their sources. Report an uneditable missing system-controlled value outside the form rather than inventing it or claiming full verification.


### Native save-dialog recovery

A successful fill or a local edited view is not a saved correction. If a save click times out while a native confirmation is open, inspect the actual dialog and use the controller's documented dialog handling within the existing save authorization. When a handler returns dialog metadata, verify its message and handled outcome; do not infer rejection or success from the timeout alone. Requery the existing record identifier, read the raw narrative value, and compare it with the expected body before describing the correction as applied. For a browser textarea, CRLF and LF may be compared as logical line endings; do not trim, collapse spaces, remove blank lines, or normalize punctuation. An unresolved confirmation or a mismatch keeps the correction unfinished, even if the candidate was entered or saved to a local text file.

## Required packet completeness gate

Bind this gate to the user's authorized packet scope first. If the responsible office supplied a curated form bundle, inventory its actual form pages before consulting broader manuals. Checklist references to absent forms are not additions to the user's authoring scope. Reconcile each active generated file to an included form or an explicit exception, exclude unrequested agent-created forms and sidecars, and do not reintroduce them while resolving generic checklist items. A retained user's original or separately requested visual is not an extra generated submission form. Report preparation within that scope separately from formal submission or office acceptance.

When attaching expense evidence, inspect the user's requested or applicable prior same-workflow naming and order before selecting files; scanner-generated names may obscure their role. When names need correction, stage renamed copies that follow the relevant convention and accurately describe each file, including combined scans, without silently splitting or changing the originals. Compare each copy to its source and check the intended order. After an authorized upload, reopen the destination and verify its actual attachment names and count; staged files alone do not establish completion.

Before a post-event packet is called complete, derive an independent list of every applicable form, physical or electronic attachment, and evidence requirement from the current programme-specific notice and the relevant expense-method provisions. Map each role to its exact prepared file, a user-managed physical attachment, or an explicit pending user/office action; check the saved contents, not filenames alone. Distinguish a transaction statement from a card voucher, a submitted original from a later edited presentation, and a payment application from a completed transfer. When the user says they retain or will attach a voucher themselves, preserve the designated blank area and classify it as user-managed. Do not infer that it does not exist, label it missing or deficient, request it, or raise an additional attachment burden solely because it was not available to the agent; follow any explicit instruction not to address it. A user-managed classification does not establish that it was attached, submitted, or waived by the applicable rules. Keep requested physical-paste space blank and intact; do not invent dates, signatures, vouchers, or payment status.

Use `scripts/verify_required_packet.py <private-inventory.json>` before handoff. Its `requirements` list must be independently transcribed from the manual, with unique `id` and `source` for each role; `artifacts` maps those ids to `ready`, `pending`, `user_action`, `user_managed`, or `not_applicable`, file `paths`, and a specific `verification` or outstanding action. For each ready HWPX, add `title_band_checks` with one entry per output `path`. Each entry contains `bands`: each band specifies the original `master` path, `master_section`, zero-based `master_table`, `target_section`, zero-based `target_table`, `title_row`, `title_col`, `first_content_row`, and `source`. Choose the cutoff from the original form: it is the first actual labelled business-field row after the title area, not a blank decorative row. The helper checks every originally blank cell above that row and the title anchor. A user-authorized addition in such a cell requires an exact `exceptions` entry with `row`, `col`, `expected`, and a user instruction as `source`. If a form has no applicable title band, use `not_applicable: true` with its actual `master`, `source`, and a specific `reason`; do not use it to skip an existing band.

When a physical attachment is explicitly user-managed, record that role as `user_managed` with empty `paths`, plus `user_management` containing `kind: explicit_user_instruction`, `medium: physical`, `action: retain` or `attach`, the conversation `reference`, and the user's exact `quote`. Independently confirm that the quote actually assigns that role to the user; the helper cannot authenticate or interpret the instruction. Run the helper with `--preparation-scope` for this authorized preparation review. Its scoped PASS does not prove the attachment exists, was pasted or submitted, or that an institutional requirement was waived. The default full-packet check does not accept `user_managed` as ready; ordinary `pending` and `user_action` roles still block a preparation-scope pass. Do not mislabel a required user-managed item as `not_applicable` or `ready` merely to obtain a pass.

The inventory must also contain `expense_reviews`, one entry per actual cost category, each with `category`, the current governing `source`, and an `items` list independently transcribed from that category's checklist. Each item has `label` and `status`: `required` needs a `requirement_id` matching a listed role; `not_applicable` needs a concrete `reason`; `pending` blocks completion. Include the programme-specific list as requirements too; a broad category checklist may contain items that apply only conditionally. Missing category review, an unresolved condition, an unexplained exclusion, or an unmapped required form blocks the packet.

The packet checker calls `scripts/verify_title_band.py` for every declared band and fails an otherwise ready role when the check is missing, uncheckable, or contains unexpected text. It still cannot assess authenticity, other field values, source authority, standalone paragraphs, or page appearance: inspect those independently. Apply the check even when a prefilled derivative already contains text, and compare against the authoritative original rather than treating the derivative as proof. Report genuinely unresolved issues within the scope reviewed; do not describe a user-managed attachment as missing or deficient solely because it was not inspected. When the user supplies evidence for an actual missing role, update only affected roles and rerun the applicable gate.

Establish who prepares each procurement document and how it reaches the submitting unit before generating a settlement packet. Possession of an older completed inspection form does not establish that the requesting unit must prepare or sign a new one. When the user confirms that another office receives delivery photographs, prepares the inspection record, and returns the complete packet, preserve that handoff and use the returned record for system submission. Label an already generated local inspection draft as reference-only in the working checklist; do not ask for duplicate signatures or silently replace the issuing office's record. Verify the saved processing order, document-role table, and system-attachment list all agree on the preparer and handoff, and keep unperformed photo delivery, packet receipt, and submission pending. Attribute a user-confirmed workflow to the user rather than presenting it as an independently verified institutional rule.

Treat a person-associated place label as a lookup clue, not extra wording to append to a confirmed building/room. Use the latest explicit room designation at every corresponding venue field, separated by activity; do not carry one activity's room into another. If the user removes an office/owner suffix, update the independent exact-cell expectations first, then require that suffix to be absent from all affected saved venue fields and previews. Preserve unrelated names, meeting titles, and source records.

When the user expands a room-only answer with a building name, replace the complete expected venue in the field inventory before patching the current document. Verify the combined building/room value in the exact saved cell and current render; finding the room number alone cannot pass the venue check. Do not alter an independently confirmed date or infer a different inspector from that clarification.

Before asking for a missing expense-form value, inspect the actual current form and map the requested fact to its required field. A form with only an operating venue and proposed merchant does not establish a separate dining-location requirement; do not block drafting with that extra question. Ask only when the form, applicable rule, or requested decision actually needs the missing value. Before handoff, verify those existing fields against the user's answers and confirm that no invented dining-location field, duplicate venue request, or unsupported venue note was added.
