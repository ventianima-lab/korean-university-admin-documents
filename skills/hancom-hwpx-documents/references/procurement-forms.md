# Procurement forms and evidence pages

Read this reference before proposing a programme budget, including a chat estimate, or drafting or revising purchase preapproval, expense settlement, vendor quotations, receipt attachment forms, or evidence-photo pages. Use the user's current edited files as the baseline. Keep active records in their working folder when the user requests that; organization is not permission to archive them.

## Permission and factual fields

- A request to prepare a document includes the user's clearance with the named vendor or party for that preparation and requested use of supplied names, seals, and signatures. Do not ask whether that permission exists or request it again.
- Treat dates, amounts, and party instructions supplied by the user as source facts. Distinguish missing business data from permission; inspect context and files before asking only for a value necessary to finish. Do not infer missing approval states or create an absent signature image.
- Use an existing supplied stamp or signature image when requested. Preserve its identity and proportions; do not draw, generate, or substitute a new seal. Preparation does not authorize sending or submission.

## Before answering and preparing post-event forms

Before quoting an amount or asking the user to confirm it, inspect the live preapproval and payment forms and bind the instructor category, rates, duration, manuscript fee, and approval status to their governing sources. Prior conversations or memory are search clues, not the basis for superseding a user-confirmed approved category. If they conflict, explain the current source and recalculate before asking. On a correction, discard the earlier expected-value map and verify the corrected category, each amount, and total in every in-scope saved form.

For post-event reports, proactively read supplied signed attendance and survey scans before leaving outcome fields blank. Reconcile actual signatures and each answered question against the roster, document the response denominator, and use the latest complete scan. Distinguish a payment application from a completed transfer using required existing fields and the approved workflow. Do not add a parenthetical status note or restore one the user removed merely to explain the distinction; if the form lacks an approved status field, communicate the status outside the form unless the governing authority requires it there. Preserve unsupported signer-controlled fields.

## Required packet completeness gate

When attaching expense evidence, inspect the user's requested or applicable prior same-workflow naming and order before selecting files; scanner-generated names may obscure their role. When names need correction, stage renamed copies that follow the relevant convention and accurately describe each file, including combined scans, without silently splitting or changing the originals. Compare each copy to its source and check the intended order. After an authorized upload, reopen the destination and verify its actual attachment names and count; staged files alone do not establish completion.

Before a post-event packet is called complete, derive an independent list of every applicable form, physical or electronic attachment, and evidence requirement from the current programme-specific notice and the relevant expense-method provisions. Map each role to its exact prepared file or an explicit pending user/office action; check the saved contents, not filenames alone. Distinguish a transaction statement from a card voucher, a submitted original from a later edited presentation, and a payment application from a completed transfer. Keep requested physical-paste space blank and intact; do not invent dates, signatures, vouchers, or payment status.

Use `scripts/verify_required_packet.py <private-inventory.json>` before handoff. Its `requirements` list must be independently transcribed from the manual, with unique `id` and `source` for each role; `artifacts` maps those ids to `ready`, `pending`, `user_action`, or `not_applicable`, file `paths`, and a specific `verification` or outstanding action. For each ready HWPX, add `title_band_checks` with one entry per output `path`. Each entry contains `bands`: each band specifies the original `master` path, `master_section`, zero-based `master_table`, `target_section`, zero-based `target_table`, `title_row`, `title_col`, `first_content_row`, and `source`. Choose the cutoff from the original form: it is the first actual labelled business-field row after the title area, not a blank decorative row. The helper checks every originally blank cell above that row and the title anchor. A user-authorized addition in such a cell requires an exact `exceptions` entry with `row`, `col`, `expected`, and a user instruction as `source`. If a form has no applicable title band, use `not_applicable: true` with its actual `master`, `source`, and a specific `reason`; do not use it to skip an existing band.

The packet checker calls `scripts/verify_title_band.py` for every declared band and fails an otherwise ready role when the check is missing, uncheckable, or contains unexpected text. It still cannot assess authenticity, other field values, source authority, standalone paragraphs, or page appearance: inspect those independently. Apply the check even when a prefilled derivative already contains text, and compare against the authoritative original rather than treating the derivative as proof. Report an incomplete packet as such. When the user supplies missing evidence, update only affected roles and rerun the gate.
