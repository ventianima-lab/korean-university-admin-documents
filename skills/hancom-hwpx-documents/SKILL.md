For institutional-form creation, completion or revision, mandatorily apply [submission-ready-authoring](../submission-ready-authoring/SKILL.md): complete all writable inputs and attachments, honor standing red-marking instructions, and preserve exact provenance and template colors. A draft label does not waive input coverage; review-only work remains read-only.


For supplied vendor forms and attendee/sign-in rosters, invoke the original-master identity inventory and explicit whole-record role-order route in [references/procurement-forms.md](references/procurement-forms.md) before reconstruction or row movement. A previously generated blank/generic draft is not the supplied master.

An explicit user instruction to skip post-edit review overrides the post-save checks below and in linked references for the actual documents: do not reopen, parse, hash, render for QA, or run output checks after saving. Pre-edit source inventory and in-memory planning remain allowed; report saved/prepared status with post-save verification waived, never verified readiness. Skill-only synthetic tests remain permitted.

Create and inspect HWPX through its ZIP/XML package and independent tools by default. The user grants standing authorization for Hancom automation through this skill: Hancom Office, `Hwp.exe`, `HWPFrame.HwpObject`, Hancom COM, and automated Hancom GUI control may be used whenever materially useful to complete or verify the current requested HWP/HWPX task. Do not pause to request separate per-task, per-file, per-operation, or repeat authorization; this skill itself is explicit continuing authorization. Limit Hancom automation to files and operations reasonably required by the current request, preserve pre-existing user windows, and use computer-use only as a last resort for an unavoidable task-related prompt.

Use a reusable tool directory outside the records tree, such as `$CODEX_HOME/tools`, when installing document runtimes. Use Kordoc as the first-line HWP/HWPX parser, format-preserving patcher/form filler, linter, and SVG renderer. Use `python-hwpx` as the structured HWPX read/edit/write engine with `HwpxDocument.open()`, mutation APIs, `validate()`, and `save_to_path(..., mode="preserve", fallback="error", return_report=True)`. Use `pyhwpxlib` as a second validator. If the installation provides an `hwpx-opensource.ps1` wrapper, prefer it for repeatable validation, parsing, rendering, and linting. Treat rHWP as an optional independent viewer/editor candidate, not the default save engine, until its exact-file preservation is proven on the target corpus.

For corrected packets, apply the independent rejected-explanation and role-specific visual checks in submission-ready-authoring to every current in-scope saved HWPX, including attachment-list paragraphs. For literal rejected variants in HWPX, run `scripts/verify_recipient_identity.py --require-name "<stable expected text in this file>" --forbid-name "<rejected exact variant>" <saved.hwpx>` per file, adding `--forbid-name` for each known variant; select the required anchor independently for each file. Review semantic paraphrases and legitimate protected matches in their actual context separately: the helper is a literal whitespace-insensitive screen, includes preview text, and cannot determine field meaning, image contents, or full packet scope. Reconcile source-mapped substantive cells with the existing template-inventory or exact-field checker and inspect each image slot in a fresh final render; passing text checks alone cannot establish either substantive sufficiency or visual category coverage.

## Mandatory Hancom COM security gate

- Before the first Hancom COM or GUI automation in a task, run `scripts/test_hancom_security_module.ps1` and require `REGISTERED=True`. A failed preflight blocks all document access.
- Every PowerShell helper and every ad hoc COM command must dot-source `scripts/hancom_com_guard.ps1` and create each COM object with `New-HancomGuardedObject`. Do not instantiate `HWPFrame.HwpObject` directly outside that guard.
- The guard fixes the module name to `FilePathCheckerModuleExample` and requires `RegisterModule('FilePathCheckDLL', 'FilePathCheckerModuleExample') == true` before visibility changes, `SetMessageBoxMode`, `Open`, `Save`, or `SaveAs`. Do not expose a caller override for the module name.
- `SetMessageBoxMode` may be enabled only by the guarded constructor after successful registration. Use `Close-HancomGuardedObject` only when the whole application object is verified to be exclusively task-owned: the helper calls `Quit`, so it must not be used on an object whose application scope is unverified or shared. If binding fails, do not open a document or invoke `Quit`; release only caller-held COM references when demonstrably safe, and report unresolved process cleanup.
- Before native access, on a sharing violation, and after final native verification, apply [references/hancom-lock-ownership.md](references/hancom-lock-ownership.md). Establish actual lock/object ownership before a user close request; an automation flag or attempted `Quit()` is not ownership or release evidence. Recheck task-attributable locks after cleanup while preserving pre-existing objects.
- After adding or changing a Hancom PowerShell helper, run `scripts/test_hancom_guard_contract.ps1`. Direct COM construction, direct registration, shortened module names, or file access without the shared guard are hard failures.

## 금액 및 자동 합계 검증

- 구매 사전품의의 산출근거는 품목명과 `단가 × 수량`을 중심으로 간결하게 작성한다. 상세 모델·중량·색상·포장 구성은 견적서 또는 규격 붙임에 두되, 같은 품목명이 반복되면 금액·수량·순서로 각 견적과 대응할 수 있어야 한다. 공식 양식이 요구하는 규격은 생략하지 않는다.
- 배송비·할인이 합계에 영향을 주면 계산 근거를 본문 또는 해당 견적에서 추적할 수 있게 한다. 사용자가 줄인 문구를 원복하거나 금액을 임의로 바꾸지 말고, 산식과 표시 금액이 다르면 누락된 조건을 별도로 알린다.
- 사용자가 수정한 공문의 문단 나눔, 표 안 정렬, 글꼴·크기 및 지급수단 표기를 후속 작업의 기준으로 삼는다. 상세 설명을 다시 늘리거나 모든 셀에 새 문단 서식을 강제로 적용하지 않는다. 같은 한글 설치에서 작성본과 수정본을 출력하여 표의 쪽 분리와 전체 쪽 수를 비교한다. 한 사례의 쪽 수를 다른 공문에 일률적으로 강제하지 않는다.
- 법인카드 식별정보는 사용자가 제공한 범위에서 비고·지급수단 칸에 반영한다. 확인란은 사용자 표시를 보존하며, 문서 작성이나 검증을 마쳤다는 이유만으로 미표시 확인란을 체크하지 않는다.

- 금액이 있는 표를 작성·수정할 때는 표시 문자열만 확인하지 말고 자동 합계·계산 필드의 존재를 먼저 검사한다. HWPX의 `hp:fieldBegin type="FORMULA"`와 연결된 필드 끝, `Formula`, `Command`, `LastResult`, 표시 결과를 함께 확인한다. 행 추가·삭제 후에는 계산 범위에 모든 대상 행이 정확히 포함되는지 검사한다.
- 각 표의 항목 금액을 독립적으로 다시 계산하여 소계·합계·집행누계·잔액과 대조한다. 같은 금액이 반복되는 본문, 붙임, 각 페이지도 위치별로 검증한다. 문서 어딘가에 정답 숫자가 있다는 문자열 검색만으로 합계 검증을 통과시키지 않는다.
- 자동 합계를 유지하려면 계산 범위, 내부 저장 결과, 표시 금액이 독립 계산값과 일치해야 하며, 저장 후 한글에서 다시 열고 필드 재계산 후에도 같은 값인지 확인한다. 이를 신뢰성 있게 검증할 수 없으면 해당 자동 계산 필드를 완전히 제거하고 직접 계산한 금액을 일반 텍스트로 넣는다. 보이는 숫자만 덮어쓰고 이전 계산식이나 캐시를 남기지 않는다. 필드 제거 시 대응 시작·끝과 관련 메타데이터만 처리하고 서식 및 다른 필드는 보존한다.
  - 계산 필드의 시작·끝을 삭제한 뒤 부모 `hp:ctrl`이 비면 그 빈 래퍼도 삭제한다. 빈 `hp:ctrl`이 남은 파일은 XML·구조 검증을 통과해도 설치 한글에서 열 때 프로세스가 종료될 수 있다. 수정한 셀에 빈 제어 래퍼와 해당 필드의 시작·끝 참조가 남지 않았는지 검사하고, 정확한 저장본을 한글에서 다시 열어 쪽 수와 직접 계산한 합계를 확인한다. 다른 제어 요소와 셀 서식은 보존한다.
- 수정 후에는 실제 저장 파일의 본문과 현재 렌더를 다시 대조하고, 미리보기 텍스트·이미지도 이전 금액을 표시하지 않도록 갱신·확인한다. 복사된 이전 미리보기는 검증 근거로 사용하지 않는다. 금액 불일치가 남으면 완료로 보고하지 않는다.
- 사용자가 금액을 직접 고쳤으며 스킬 반영만 요청했다면 문서를 다시 저장하거나 덮어쓰지 않는다.
